# C-B04 INT 与 VARCHAR 的行序列化

## 课程依据

G-P5、G-P8；C-S27、C-S28；D-S6、D-S15、D-S20

课程要求INSERT把值转为页记录、SELECT恢复行。INT32、UTF-8和255字节VARCHAR上限是统一项目边界。

## 任务目标

按传入schema顺序将tuple值编码为紧凑字节，并精确解码回来。INT占4字节有符号little-endian；VARCHAR为2字节无符号字节长度加UTF-8内容，最长255字节。基础格式无NULL位图或字段名，不允许额外尾字节。编码错误在页写入前发现，防止留下半条记录。

## 预期代码结构解释

- RowCodec.encode(columns,values)->bytes：先检查列数和每个值的确切类型，INT排除Python bool；检查-2147483648至2147483647。VARCHAR先encode('utf-8')再计算长度。所有字段验证成功后拼接，函数无磁盘副作用。
- decode(columns,payload)->tuple：维护游标，INT读4字节；VARCHAR先读取2字节长度，再读取指定字节并严格UTF-8解码。每一步验证剩余长度，结束要求cursor==len(payload)，避免默默接受损坏尾部。
- 错误上下文：不支持FLOAT、NULL或持久化BOOL；报告字段序号/列名、期望类型及实际值类型。解码损坏为RowDecodeError；TableHeap捕获后补page_id与RID，不在codec伪造SQL行列。
- 易错点：不能用str(value)兜底，否则语义层遗漏的类型错误会被悄悄持久化；不能按字符长度截断UTF-8。
- 整合范围：用冻结ColumnMeta构造schema，不依赖B；C-B06用本codec编码普通表和Catalog特殊表。

## 测试用例

1. `test_exact_binary_layout`

   - 输入：schema=(INT,VARCHAR,INT)，values=(1,'Alice',20)。
   - 必须断言：payload为010000000500416c69636514000000的十六进制字节，长度15；解码回相同tuple。

2. `test_int32_boundaries`

   - 输入：编码-2147483648、2147483647及各自越界1的值。
   - 必须断言：两个端点往返相等；越界抛RowEncodeError；True也被拒绝，不能当作整数1。

3. `test_utf8_byte_limit`

   - 输入：VARCHAR分别为''、'汉'×85、'汉'×86。
   - 必须断言：空串编码0000；85汉长度前缀255且总257字节；86汉因258字节超限失败。

4. `test_decode_truncation_and_garbage`

   - 输入：INT只给3字节；VARCHAR长度5只给4字节；非法UTF-8；合法行后加00。
   - 必须断言：四项均RowDecodeError，含字段或游标信息；不返回部分行。

5. `test_schema_order_and_types`

   - 输入：schema=(VARCHAR,INT)，值('张三',-2)；另测列数不足、NULL、FLOAT和字符串充当INT。
   - 必须断言：合法行往返且字段顺序不变；其余输入均在encode阶段失败，无文件I/O调用。
