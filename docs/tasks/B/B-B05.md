# B-B05 四类 SQL 的 Logical Plan 与只读编译管线

## 课程依据

G-P3、G-P5、G-P7、G-P8；C-S3、C-S29、C-S30、C-S31、C-S32、C-S43；D-S10、D-S17

课程要求由 AST 经语义检查生成可展示、可执行的计划。本任务补充 DELETE 的 DeletePlan，并保留 SeqScan 的行身份；这些节点是独立开发的公共契约。

## 任务目标

实现 build_plan(bound_stmt) 和 CompilerPort.compile 的组合入口。CREATE 生成名称与列定义；INSERT 生成表元数据与 schema 顺序值；SELECT 总是生成 Project，下面按有无 WHERE 连接 Filter 和 SeqScan；DELETE 使用 DeletePlan 包住扫描或过滤树。所有 Plan 不可变，compile 无表号分配、Catalog 注册和存储调用，语义失败时不产生执行计划。

## 输入输出

输入是手工构造或前端产生的冻结 AST、Catalog 元数据与版本化扩展信封；输出是 Bound AST、Logical Plan、优化后 Plan 或结构化语义/计划错误。不得读写真实数据页。

## 公共接口

`CatalogPort`、`CatalogRepositoryPort` 与 `CompilerPort.compile/optimize`；输入为冻结 AST/扩展信封，输出为 Bound 节点、Plan 节点或版本化扩展信封。

扩展不得直接改变冻结 AST、Bound AST、Plan 或 Protocol；跨层扩展统一使用 `ExtensionStatement`、`BoundExtension`、`ExtensionPlan(feature, version, payload, span)`。

## 实现步骤

1. 先写四类 Bound 输入与期望计划形状；用递归结构断言而非仅比较打印字符串。
2. 实现 Planner 分派和 compile 门面，保留 span；对未知节点产生明确内部契约错误，不能返回 None 当成功。
3. 用记录型 FakeCatalog 和诊断回调证明编译只有读取，语义失败不会发出成功 Plan 事件。

## 预期代码结构解释

- Planner.build_plan(bound_stmt)->PlanNode：按四类 Bound 语句分派，不重新查找列名或再次做 INSERT 重排。SELECT 输出 Project(indices,names)，where=None 时直接连接 SeqScan。
- build_delete(bound)->DeletePlan：child 为 SeqScan 或 Filter(SeqScan)，table 与扫描元数据一致；禁止插入 Project，从结构上保证执行器收到 StoredRow 及 RID。
- Compiler.compile(statement,catalog)：固定顺序 analyze→build_plan。可通过构造时注入的只读诊断回调记录 Semantic 和 Plan，不变更公共 compile 签名，不执行 optimize 或 Executor 以外的隐式操作。
- 易错点：不能用 AST 分支直接调用 StoragePort，也不能用 compile 来分配 CREATE 的表号。解释查询和重复编译应保持数据库状态不变。
- 整合范围：用手工 AST 和 FakeCatalog 独立验证；集中整合把 A.parse 的语句送入 compile，再单独 optimize，最后由 D Executor 执行。

## 测试用例

1. `test_select_plan_shape_with_and_without_filter`

   - 输入：分别绑定 SELECT name WHERE age>=18 与 SELECT * 无 WHERE。
   - 必须断言：前者 Project(indices=(1,))->Filter->SeqScan；后者 Project(indices=(0,1,2))->SeqScan；元数据和 Span 正确。

2. `test_insert_plan_contains_schema_order_values`

   - 输入：用户列 age,id,name，绑定值已为 (1,'Alice',20)。
   - 必须断言：InsertPlan.values 精确为 (1,'Alice',20)，不再次置换；table_id 与 Catalog 一致。

3. `test_create_plan_does_not_allocate_identity`

   - 输入：compile 合法 CREATE，Fake 的 allocate/register 均设置为一调用就失败。
   - 必须断言：得到 CreateTablePlan(name,columns)，不包含伪造 table_id 或首页；Fake 写方法无调用。

4. `test_delete_plan_retains_rid_path`

   - 输入：分别绑定 DELETE 全表与 WHERE id=1。
   - 必须断言：DeletePlan.child 分别为 SeqScan、Filter(SeqScan)，树中不存在 Project；Delete.table 与 Scan.table 相等。

5. `test_compile_stops_after_semantic_failure`

   - 输入：SELECT missing FROM student，记录 planner 调用次数与诊断事件。
   - 必须断言：Semantic 错误向上传播；build_plan 调用 0 次；无成功 Plan 事件、无写入，错误 Span 保留。

## 理解考试与小修改

- 讲解题：SELECT 中 FROM、WHERE、SELECT 的书写顺序为什么没有变成同样顺序的嵌套？
- 答案要点：父算子拉取子算子的结果；Project 从 Filter 取合格整行，Filter 从 SeqScan 取原行，因此执行依赖决定树从下向上组织。
- 现场小修改：给 DELETE 无 WHERE 增加整树断言和一张 RID 流向图，解释误加 Project 会使哪个 D-B04 测试失败。
