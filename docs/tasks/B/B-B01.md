# B-B01 CatalogService、名称规范化和缓存

## 课程依据

G-P3、G-P6、G-P8；C-S24、C-S25；D-S14、D-S17、D-S18

材料要求维护表列结构并持久化系统元数据。本任务承担内存服务和 Repository 协调，页式持久化由 C-B06 完成；名称小写化和先保存后更新缓存是本项目约定。

## 任务目标

实现 CatalogPort：启动时一次加载 TableMeta，按规范表名建立索引；支持查表、列表、发号和注册。查询方法没有存储副作用。表号取已加载最大编号加一与注入初值的较大者，递增且允许空洞。注册先检查重复表名、表号、列名和连续列序，再调用 Repository 保存，成功后更新内存；正常重启能得到同一元数据。 next_id取max(已登记最大ID+1,initial_next_table_id)，注入值来自C持久化下界；有效ID至2147483647，耗尽写前拒绝。

## 预期代码结构解释

- CatalogService(repository,initial_next_table_id=1)：验证 TableMeta 正表号、唯一名称和连续列序；next_id=max(最大表号+1,注入初值)。integration 从 C 的 Superblock 注入初值；空库默认 1，损坏元数据报错。
- get_table(name)、table_exists(name)、list_tables()：ASCII casefold 后查找，缺表报告名称；列表按 table_id 排序并返回新容器，调用方不能修改内部索引。源 Span 由语义调用层补充，不伪造 SQL 行列。
- allocate_table_id() 与 register_table(table)：前者只推进服务计数器，后者先验证、后 save_table、再更新索引和最大编号。保存失败内存不出现新表；禁止编译路径调用发号或注册。
- 易错点：缓存查询不得顺手保存；allocate 不意味着表已创建。Fake 的重启测试仅证明接口行为，真实磁盘重启仍由集中整合验收。
- 整合范围：独立验收使用 FakeRepository；integration 注入 C-B06 Repository 和 Superblock.next_table_id。D-B03 在执行时发号，C.create_table 持久化推进计数，避免失败留下的编号重启后复用。

## 测试用例

1. `test_empty_catalog_allocates_unique_ids`

   - 输入：FakeRepository 返回 []，连续发号两次。
   - 必须断言：返回 1、2；load 调用 1 次；save 为 0 次；list_tables 仍为 []。

2. `test_reload_normalizes_and_preserves_schema`

   - 输入：加载 table_id=7、name='student'、列 id/INT/0、name/VARCHAR/1、first_page_id=3；查询 STUDENT；分别注入 initial_next_table_id=1 和 12。
   - 必须断言：返回相同表结构；两个服务下一编号分别为 8、12；修改 list_tables 返回列表不影响后续查询。

3. `test_register_rejects_duplicate_before_save`

   - 输入：已有 student，分别注册同名大小写变体、重复 id 或 ordinal=[0,2] 的元数据。
   - 必须断言：每次产生 Catalog 错误；Fake save 计数保持 0；原缓存完整，错误含冲突名称或列序原因。

4. `test_repository_failure_does_not_publish_cache`

   - 输入：注册合法新表时 Fake.save_table 抛出预定 StorageError。
   - 必须断言：同一错误向上层传播；table_exists 为 False；缓存无新条目；不宣称磁盘事务回滚。

5. `test_register_then_reload`

   - 输入：向可记忆 Fake 注册表号 9 的合法表，再创建新 CatalogService。
   - 必须断言：save 恰一次；新服务可查到列顺序和首页号；下一表号为 10。

6. `test_catalog_id_high_water`

   - 输入：目录最大3，initial_next_table_id=7；另设已耗尽标记2147483648。
   - 必须断言：首次发号7；耗尽抛ID_EXHAUSTED且无save。

## 理解考试与小修改

- 讲解题：register_table 为什么不能先把表加入缓存再调用 save_table？
- 答案要点：保存失败时内存会宣称表存在而重启后消失；应先做全部元数据验证，持久化成功后发布缓存。I/O 中途失败仍不具备事务原子性。
- 现场小修改：给 list_tables 增加稳定排序测试：以 9、2 的顺序加载，输出必须为 2、9；解释它为什么不改变 Repository 接口。
