## 实现步骤

## 预期代码结构解释

- parse_table_ref：规范化表名和别名，未写 alias 用表名作引用名，不访问 Catalog。
- parse_join：固定一段 INNER JOIN 和必需 ON；连接条件复用表达式，不生成执行循环。
- parse_column_ref：把 a.id 作为两个名称字段，不能丢掉 qualifier；未限定名称仍保留 Identifier 供 B 判断歧义。
- 易错点：A 保留未限定列让 B 诊断歧义，不能凭左右位置猜测它属于哪张表。
- 整合范围：独立验收只检查 payload；完整 JOIN 需要 B-E06 和 D-E05。两表之外的连接链需要新版本扩展契约。

## 测试用例

1. `test_a_e04_join_payload`

   - 输入：SELECT s.id,c.name FROM student AS s JOIN class c ON s.cid=c.id;
   - 必须断言：左右表及别名正确；ON 左右字段保留 qualifier；投影顺序 s.id、c.name。

2. `test_a_e04_join_where`

   - 输入：SELECT s.id FROM s INNER JOIN c ON s.id=c.id WHERE s.id>1;
   - 必须断言：on 与 where 分别编码且不互相覆盖，join_type=INNER。

3. `test_a_e04_missing_on`

   - 输入：SELECT s.id FROM s JOIN c;
   - 必须断言：在分号报期望 ON，不自动生成笛卡尔积。

4. `test_a_e04_reject_outer_join`

   - 输入：SELECT * FROM s LEFT JOIN c ON s.id=c.id;
   - 必须断言：明确拒绝未支持 LEFT JOIN，不降级为 INNER JOIN。

## 理解考试与小修改

- 讲解题：为什么 a.id 与 b.id 不能都转成 Identifier(id)？
- 答案要点：限定符参与名字绑定，丢失后两列无法区分，连接条件可能被错误绑定成同一列。
- 现场小修改：增加左右表别名相同的语法 fixture，保留两份别名供 B 报重复引用名。
