## 输入输出

输入是手工 Plan、冻结 Bound 表达式与注入的 Fake/真实端口；输出是 ExecutionResult、格式化结果、Trace 或结构化执行错误。不得自行解析 SQL、猜测 schema 或绕过 StoragePort。

## 公共接口

`ExecutorPort.execute(plan) -> ExecutionResult` 与 `ApplicationPort.execute(source, trace)`；只消费冻结 Plan/扩展信封和注入端口，不直接导入其他成员实现。

扩展不得直接改变冻结 AST、Bound AST、Plan 或 Protocol；跨层扩展统一使用 `ExtensionStatement`、`BoundExtension`、`ExtensionPlan(feature, version, payload, span)`。

## 实现步骤

1. 编写带调用顺序日志的两个Fake。
2. 实现成功路径和重复表检查。
3. 向create、register和flush注入独立失败，证明失败不打印成功。

## 预期代码结构解释

- execute_create：写入前防御性检查名称是否已存在；表号只在执行时申请，first_page_id来自storage。注册成功后才返回结果；元数据不可用猜测页号。
- execute_insert：使用plan.table和plan.values，不再次解析INSERT列列表。真实RID可以进入Trace，用户结果保持统一ExecutionResult结构。
- flush边界：每条成功写语句持久化，正常退出再flush。write或save失败时保留异常上下文，提示阶段/表/IO原因，不能把错误视为受影响0行。
- 易错点：Catalog是逻辑元数据服务，不由D偷偷用JSON文件代替。IO失败后已写部分数据可能存在，恢复属于扩展。
- 整合范围：两个Fake都只在tests/runtime中；装配时使用B的CatalogService和C的真实存储。
